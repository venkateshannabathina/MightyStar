# WP1 — Conversation Store and Memory v1

19 October 2026. Implemented for review; **`MIGHTY_MEMORY_V1` remains off by default**. WP2 has not started. The native app and its backend must inherit the same flag. No installed app was replaced. Verification uses isolated databases and synthetic conversations.

## Behavior

With the flag on, typed chat posts `{characterId, userMessage, clientTurnId, attachments?}` to `/api/chat`, with an 8 KiB encoded-body limit. Existing display history stays in UI localStorage and is not migrated or uploaded as context. The frontend registers a character once per profile change, then sends only the current turn; retries retain the same ID. Completed non-private requests reuse the stored result instead of adding duplicate turns. The flag-off path keeps the existing `{character, messages}` behavior.

Calls retain their version-2 session negotiation and PCM transport. Character metadata is still accepted once at session open. Text turns accept `userMessage`, `characterId` and `clientTurnId`; voice turns use the existing ticket's turn UUID and add matching identity fields. UI/native history upload is disabled for memory-enabled calls. Backend context comes from the same store as typed chat. Existing speech/renderer version 1 and the non-streaming chat JSON format remain intact.

The native editor's existing Memory tab now lists learned facts, edits/saves them, deletes them, exports JSON, forgets learned context and shows the compiled character card. Save compiles the card before completing the profile save. Existing characters without a backend profile are registered on first use; this is a one-time profile save, not a history migration. Card and source hash are stored in the backend profile row and copied into the UI profile on save.

“Forget conversation and memories” removes learned facts, rolling state, backend turns and request-result cache for this character. It retains the authored character profile and the UI display cache, as explained by the confirmation. Deleting one fact removes it immediately from semantic/core retrieval and clears the rolling summary; it does not rewrite old transcript text. In-flight learning is fenced by per-character revisions, so deleted/forgotten facts cannot be reinserted by older jobs. Physical forensic erasure of SQLite backups/journals is not claimed.

## Storage and packaging

- Database: `~/Library/Application Support/Mighty Chat/Memory/memory.sqlite`. The test-only `MIGHTY_MEMORY_ROOT` override selects an isolated directory. No request can select a filesystem path. Directory permissions are 0700, database 0600; database symlinks, including dangling ones, are rejected.
- The bundled Node **v24.20.0** exposes `node:sqlite` / SQLite **3.53.4**. `DatabaseSync`, WAL, bound parameters, secure-delete and character-scoped queries implement the specified tables. Extra `profiles`, `requests` and `revisions` tables provide compilation caching, idempotency and deletion fencing. Summaries advance a fold watermark without deleting turns. No new SQLite native binding or signing step is needed. [Node SQLite documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html).
- Embeddings: pinned **bge-small-en-v1.5**, quantized ONNX, **384** dimensions, CLS pooling/L2 normalization, local CPU worker thread with one inference thread. The worker loads only packaged files and has no download/network path. The small BERT WordPiece tokenizer uses the packaged vocabulary. ONNX conversion revision and model-file SHA-256 values are in `Backend/memory/models/bge-small-en-v1.5/manifest.json`; provenance is in its NOTICE.
- Runtime: `onnxruntime-node@1.23.2`, with macOS arm64/x64 CPU libraries, plus pure-JavaScript `js-tiktoken@1.0.21`. npm lockfile and licenses are retained. Non-macOS binaries are omitted. The sign script signs inference dylibs and `.node` modules before signing/verifying the app. This reuses the existing Node process/runtime ABI instead of adding a Python ML environment to the stdlib-based Edge worker. Added uncompressed runtime/model assets are approximately **132 MiB**; that size cost is explicit. [ONNX Node platform support](https://onnxruntime.ai/docs/get-started/with-javascript/node.html).
- The isolated signed-package check successfully loaded SQLite and native ONNX from the copied app and ran real Groq persona compilation, a reply, background extraction, retry and memory controls. This Mac is arm64; Intel execution is not claimed. The existing bundled Node binary declares macOS **13.5**, although the native compiler target is 12.0; ONNX declares 13.4, so it does not raise the bundled runtime's existing effective minimum.

## Memory and prompt bounds

Working context uses at most ten message rows including the current input. Its 600-token slot reserves up to 250 for the current message and divides the remainder among recent rows; stored full turns are not overwritten by truncation. Static persona/style/mode are first and remain byte-identical across unchanged turns. Dynamic core facts, top-four retrieved facts, summary, mood/time and recent messages follow as untrusted data.

Every slot is capped by the section 5.5 table (total **2,570** content/envelope token units; acceptance with 10% headroom **2,827**). Supported o200k-family content uses a local tokenizer plus envelope allowance. Models without a verified local tokenizer use a conservative UTF-8-byte token upper bound rather than an invented exact token count; those prompts can be shorter. Truncation preserves valid Unicode. Compilation distributes its input budget among all five source fields so a long description cannot consume the entire source budget; short voice examples are preserved verbatim in the card. Neither WP2 directives nor chat streaming are introduced.

After the reply is sent, a separate task extracts facts and, every ten user turns, rewrites the rolling summary to at most 120 words / 250 token units. Private rows are excluded. Utility calls use the character's selected reply provider/model (the current owner uses Groq GPT-OSS 20B); the architecture has no separate “fast model” setting. Extraction/summary errors are contained and counted without logging content. They do not delay or invalidate the already-issued response. Utility requests have bounded input/output and a 20-second timeout.

Semantic retrieval uses cosine similarity >0.35, top four, importance/30-day recency scoring from the spec. Similarity >0.88 deduplicates and refreshes last-seen/max importance. The interface is pluggable. English BGE is verified here; multilingual quality has not been established and requires a small multilingual-model comparison before enabling for non-English use. The voice being multilingual is not evidence of embedding-language quality.

Credentials and sensitive numbers are redacted before context/storage. Known provider-key values and common API-key/password/payment/government-ID patterns are filtered. Explicit English privacy markers (for example “keep this private”, “don't remember”, “off the record”, `private:` or `[private]`) omit the turn and response from persistent context, result cache and extraction. Private input is not embedded/cached; its content is removed from any scheduled summary task. This is a conservative pattern-based safeguard, not a universal PII classifier. The UI display cache remains the user's display record under the spec's no-migration rule.

## Acceptance evidence

[Machine-readable results](wp1-evidence/acceptance.json), [signed-package receipt](wp1-evidence/signed-package.json), and [native Memory-tab screenshot](wp1-evidence/memory-panel.png) are retained. The screenshot is synthetic fixture data and was visually checked.

- **2,000 stored rows:** the test request is under 8 KiB; assembled context **1,908** token units, or **2,407** when dynamic slots are filled, below the 2,827 acceptance limit. The frontend VM test independently verifies 2,000 display rows never enter the new request.
- **500-turn recall:** a real offline BGE query retrieves the dog-name fact placed 500 stored rows earlier. This is a scripted recall test, not a broad quality score.
- **Failures:** delayed/failed extraction and failed summarization do not block a completed reply. Ten-turn summary cadence and fold-without-delete are checked. Private data, retry IDs, character isolation, edit/delete, forget races and dangling-symlink rejection are checked.
- **Routes/calls:** authenticated temporary-server checks cover default-off/no database, compact HTTP and WebSocket turns, server-owned context, profile compilation cache, retry reuse, CRUD/export and payload bounds, using a test-only provider/speech stub plus real offline embeddings.
- **Native UI:** the fixture loads a fact, invokes Save/Delete through actual controls, verifies the result, and captures the panel. The compiled-card/export/forget API paths are also exercised by the signed live check.
- Existing provider/settings/Claude routing, conversation, STT, phrase chunker/scheduler, protocol, native call/audio/network, idle bridge, player speech and native editor bridge checks pass. Native app source typecheck passes with existing deprecation warnings.
- Existing `check-character-editor.cjs` stops at an unrelated portrait assertion **4 != 3**. The same failure is reproduced with the installed pre-WP1 UI scripts, and the relevant queue functions are identical. The check and portrait implementation were not weakened or changed. Its first launch also required its external static fixture server; missing-server setup is not counted as a product failure.
